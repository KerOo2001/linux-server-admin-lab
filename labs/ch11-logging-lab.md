# CH11 - Analyzing and Storing Logs

## Objective

Practice analyzing system logs on RHEL 9 using `systemd-journald`, `journalctl`, and `rsyslog`, monitor log files in real time, filter Journal entries, inspect authentication logs, manage timezone information, and configure and verify persistent Journal storage across reboots.

---

## Lab Environment

- **Server OS:** Red Hat Enterprise Linux 9
- **Server hostname:** `Server.kero`
- **Primary user:** `kero-user`
- **Test user:** `dev1`
- **Administrative access:** `root`
- **Journal service:** `systemd-journald`
- **Syslog service:** `rsyslog`

---

## 1. Verify the rsyslog Service

The status of the `rsyslog` service was checked using:

```bash
systemctl status rsyslog
```

The service was confirmed to be:

```text
active (running)
```

and enabled on the system.

---

## 2. Review Recent Journal Entries

The last 10 entries from the system Journal were displayed using:

```bash
journalctl -n 10
```

This provides a quick way to inspect the most recent system events.

---

## 3. Filter Logs by Service

The most recent logs generated by the SSH service were displayed using:

```bash
journalctl -u sshd -n 5
```

The `-u` option filters Journal entries by systemd unit.

Logs for the SSH service from the current boot can be displayed with:

```bash
journalctl -u sshd -b
```

---

## 4. Filter Logs by Priority

Error-level Journal entries were displayed using:

```bash
journalctl -p err
```

The options can also be combined.

For example, the last three error entries from the current boot:

```bash
journalctl -p err -b -n 3
```

This combines:

- `-p err` - filter by error priority
- `-b` - current boot
- `-n 3` - display the last three matching entries

## 5. Inspect Authentication Logs

Authentication and security events were inspected from:

```text
/var/log/secure
```

The last five entries were displayed using:

```bash
tail -n 5 /var/log/secure
```

For real-time monitoring:

```bash
tail -f /var/log/secure
```

A user session was then opened with:

```bash
su - dev1
```

The live log showed the session being opened:

```text
pam_unix(su-l:session): session opened for user dev1
```

After leaving the session with:

```bash
exit
```

the log showed:

```text
pam_unix(su-l:session): session closed for user dev1
```

This demonstrated real-time monitoring of authentication events.

## 7. Understand rsyslog Rules

The main rsyslog configuration file is:

```text
/etc/rsyslog.conf
```

Example rules include:

```text
authpriv.*    /var/log/secure
cron.*        /var/log/cron
```

The selector follows the general format:

```text
FACILITY.PRIORITY
```

For example:

```text
authpriv.*
```

means authentication/security messages from the `authpriv` facility at all priorities are routed to:

```text
/var/log/secure
```

Similarly:

```text
cron.*
```

routes all priorities from the `cron` facility to:

```text
/var/log/cron
```

## 9. Review Logs by Boot

Logs from the current boot were displayed using:

```bash
journalctl -b
```

The previous boot can be selected using:

```bash
journalctl -b -1
```

Initially, attempting to access the previous boot returned:

```text
Specifying boot ID or boot offset has no effect, no persistent journal was found.
```

This revealed that the server was using volatile Journal storage.

---

## 10. Identify Volatile Journal Storage

The persistent Journal directory was checked:

```bash
ls -ld /var/log/journal
```

Initially, it did not exist.

The runtime Journal directory was then inspected:

```bash
ls -ld /run/log/journal
```

It existed under:

```text
/run/log/journal
```

The active Journal logs also reported:

```text
Runtime Journal
```

This confirmed that Journal data was being stored in volatile runtime storage.

---

## 11. Configure Persistent Journal Storage

A persistent Journal directory was created:

```bash
mkdir /var/log/journal
```

The systemd temporary-files mechanism was then used to apply the appropriate directory ownership and permissions:

```bash
systemd-tmpfiles --create --prefix /var/log/journal
```

The directory was verified with:

```bash
ls -ld /var/log/journal
```

The resulting ownership included:

```text
root systemd-journal
```

The Journal was then flushed from runtime storage to persistent storage:

```bash
journalctl --flush
```

The persistent Journal directory was inspected:

```bash
ls -l /var/log/journal
```

A machine-specific Journal directory was successfully created.

---

## 12. Verify Persistence Across Reboots

A unique test message was generated:

```bash
logger "CH11-PERSISTENT-TEST"
```

It was verified in the Journal:

```bash
journalctl | grep CH11-PERSISTENT-TEST
```

The system was then rebooted:

```bash
reboot
```

After the reboot, the same message was searched again:

```bash
journalctl | grep CH11-PERSISTENT-TEST
```

The message was still available.

Logs from the previous boot were also successfully retrieved:

```bash
journalctl -b -1 -n 5
```

This confirmed that Journal data was now persistent across reboots.

## 13. Troubleshooting Scenario

### Scenario

An administrator needs the last 10 SSH log entries from the previous system boot.

The required command is:

```bash
journalctl -u sshd -b -1 -n 10
```

This combines:

- `-u sshd` - SSH service logs
- `-b -1` - previous boot
- `-n 10` - last 10 matching entries

## Key Concepts Practiced

### systemd-journald

Collects and stores system Journal events.

### journalctl

Reads, searches, and filters entries stored in the system Journal.

### rsyslog

Processes and routes syslog messages into traditional log files such as:

```text
/var/log/messages
/var/log/secure
/var/log/cron
```

A useful mental model is:

```text
systemd-journald -> Collect / Store Journal
journalctl       -> View / Search Journal
rsyslog          -> Route / Write log files
```

---

## Volatile vs Persistent Journal

```text
/run/log/journal
```

is runtime/volatile storage.

```text
/var/log/journal
```

is used for persistent Journal storage.

Persistent storage allows logs from previous boots to remain available for troubleshooting.
