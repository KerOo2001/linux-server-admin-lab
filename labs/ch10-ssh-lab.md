## 2. SSH Key-Based Authentication

### Generate a dedicated SSH key pair

A separate ED25519 key was created on the MobaXterm client for this lab:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/rhel_lab
```

This created:

```text
~/.ssh/rhel_lab
~/.ssh/rhel_lab.pub
```

- `rhel_lab` is the **private key** and remains on the client.
- `rhel_lab.pub` is the **public key** and can be copied to the server.

### Copy the public key to the server

```bash
ssh-copy-id -i ~/.ssh/rhel_lab.pub dev1@192.168.88.129
```

The command reported:

```text
Number of key(s) added: 1
```

### Test key-based authentication

```bash
ssh -i ~/.ssh/rhel_lab dev1@192.168.88.129
```

The SSH login succeeded without requiring the `dev1` account password.

## 3. Verify authorized_keys

On the RHEL server as `dev1`:

```bash
cat ~/.ssh/authorized_keys
```

The ED25519 public key from the Windows/MobaXterm client was present.

Important distinction:

```text
Server: ~/.ssh/authorized_keys
Client: ~/.ssh/known_hosts
```

`authorized_keys` contains public keys authorized to authenticate to the account.

`known_hosts` stores SSH host identities previously seen by the client.

## 4. Inspect Effective SSH Configuration

As `root` on the RHEL server:

```bash
sshd -T | grep -E 'permitrootlogin|passwordauthentication|pubkeyauthentication'
```

Initial effective configuration:

```text
permitrootlogin yes
pubkeyauthentication yes
passwordauthentication yes
```

`sshd -T` was useful for checking the configuration that `sshd` would actually use rather than relying only on the contents of `/etc/ssh/sshd_config`.

## 5. Disable Direct Root SSH Login

The SSH server configuration was edited:

```bash
vim /etc/ssh/sshd_config
```

The following directive was added:

```text
PermitRootLogin no
```

Before applying the configuration, its syntax was tested:

```bash
sshd -t
```

No output indicated that the syntax check succeeded.

The configuration was then reloaded:

```bash
systemctl reload sshd
```

However, verification showed:

```bash
sshd -T | grep permitrootlogin
```

```text
permitrootlogin yes
```

The expected setting had not become effective.

## 6. Troubleshooting an SSH Configuration Override

To locate other active `PermitRootLogin` directives:

```bash
grep -Rni '^[[:space:]]*PermitRootLogin' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
```

The result showed:

```text
/etc/ssh/sshd_config:41:PermitRootLogin no
/etc/ssh/sshd_config.d/01-permitrootlogin.conf:3:PermitRootLogin yes
```

The additional configuration file was inspected:

```bash
cat /etc/ssh/sshd_config.d/01-permitrootlogin.conf
```

It contained:

```text
# This file has been generated by the Anaconda Installer.
# Allow root to log in using ssh. Remove this file to opt-out.
PermitRootLogin yes
```

The Anaconda-generated configuration was therefore affecting the effective SSH configuration.

For the lab, the file was moved to a backup location:

```bash
mv /etc/ssh/sshd_config.d/01-permitrootlogin.conf /root/01-permitrootlogin.conf.bak
```

The configuration was tested and reloaded:

```bash
sshd -t
systemctl reload sshd
```

Verification:

```bash
sshd -T | grep permitrootlogin
```

Result:

```text
permitrootlogin no
```

### Troubleshooting lesson

A valid configuration file does not necessarily mean the expected setting is effective.

Useful workflow:

```text
Edit
  ↓
sshd -t
  ↓
Reload
  ↓
sshd -T
  ↓
Test from a real client
```

When an expected SSH setting is not applied, inspect both:

```text
/etc/ssh/sshd_config
/etc/ssh/sshd_config.d/
```

## 9. Validate Authentication Methods

### Public-key authentication

From MobaXterm:

```bash
ssh -i ~/.ssh/rhel_lab dev1@192.168.88.129
```

Result:

```text
SUCCESS
```

The user was able to log in using the SSH key.

### Password authentication

For testing, public-key authentication was disabled on the client for that connection and password authentication was explicitly requested:

```bash
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password dev1@192.168.88.129
```

Result:

```text
Permission denied (publickey,gssapi-keyex,gssapi-with-mic).
```

Password authentication was therefore unavailable while public-key authentication continued to work.

## 10. SSH Troubleshooting Notes

Common SSH errors reviewed during the lab:

### Permission denied

```text
Permission denied (publickey,password)
```

The client reached the SSH server, but authentication failed.

Possible causes include:

- Incorrect password
- Incorrect SSH key
- Public key missing from `authorized_keys`
- Authentication method disabled by SSH configuration

### Connection refused

Usually indicates that the destination host was reached but no service accepted the connection on the requested port.

Check:

```bash
systemctl status sshd
```

and verify the SSH port.

### Verbose SSH diagnostics

For additional client-side troubleshooting:

```bash
ssh -v user@server
```

More verbosity can be requested with:

```bash
ssh -vv user@server
ssh -vvv user@server
```

## Key Takeaways

- `ssh` is the SSH client.
- `sshd` is the SSH server daemon.
- SSH uses TCP port `22` by default.
- Private keys must remain private on the client.
- Public keys can be installed in `~/.ssh/authorized_keys` on the server.
- `~/.ssh/known_hosts` is maintained on the client for known SSH server identities.
- `ssh-copy-id` simplifies public-key installation.
- `PermitRootLogin no` blocks direct root SSH login.
- `PasswordAuthentication no` disables SSH password authentication.
- Always run `sshd -t` before reloading changed SSH configuration.
- `sshd -T` helps verify the effective SSH server configuration.
- RHEL SSH configuration may include additional files under `/etc/ssh/sshd_config.d/`.
- Configuration changes should be validated with a real SSH client before considering the task complete.
